= Rule language surface syntax — options (IBAW)
:icons: font
:toc:
:toclevels: 3

Issue-based argumentation on how a rewrite-rule language should fit into
ddot.it. Successor discussion to link:TODO-rules.adoc[] (whose syntax is
SPARQL-shaped, not ddot-shaped). Structure: *Issue* → *Positions* →
*Pro/Con arguments* → *Resolution*.

[TIP]
====
This file is the *design rationale* (the debate). For the *resolved language* as
a plain reference — the `!!find` grammar, verbs, and the progressive ladder — see
link:../../../../../../../../../ddot.it-javalib/ddot-rules.adoc[`ddot-rules.adoc`] in the sibling repo `ddot.it-javalib`.
The Level-2 `!!find` surface (Position 15) is implemented in the
link:find/[`refactor.find`] package.
====

Context: ddot.it (`../../../../../../../../../ddot.it/syntax-summary.adoc`)
offers exactly three extension points, none of which are keyword blocks:

. *Commands* — `!!x` ≡ `ddot.it/x`; already scope regions (`!!on`/`!!off`)
  and take params (`!!block?end=THE-END`).
. *Metadata* — `,,` annotates a whole triple; deliberately permissive, MAY
  contain `..` freely.
. *Triples* — since v1.3 the *object* may contain `..`, so a whole pattern
  fits into an object slot.

Each extension point yields one Position below (Round 1). Round 2 questions
the premise itself.

[[i-language]]
== ISSUE 0 — Do we need a general pattern language at all?

Root-cause observation on Round 1: all five positions are *pattern languages
with variables* (`?s`, `$foo`, `?_`). Variables and explicit quantification
are the one thing ddot.it deliberately does not have — which is why every
Round-1 option feels foreign no matter the surface dressing.

Scope clarification: the language must serve *three verbs*, not one —
*query* (select/report), *check* (assert, `ddot check`), *rewrite*
(transform). Any position must be judged against all three; in particular a
pure refactoring catalog covers rewrite but not ad-hoc query.

Round 2 asks where the quantification could live instead:

[cols="1,2,2",options="header"]
|===
| Position | Quantification lives in… | See

| L1 — general pattern language | variables in the rule text | Round 1, <<p1>>–<<p5>>; standardized: <<p14>>, <<p15>>
| L1½ — single *implicit* focus variable | the hole in an incomplete triple + ddot's omitted-subject sugar | <<p13>>
| L2 — fixed catalog of named refactorings | the *semantics of standard relations* (declarative) or *CLI verbs* (imperative) | <<p6>>, <<p8>>
| L3 — rules derived from examples | a concrete edit / before-after pair, generalized by the engine | <<p9>>, <<p10>>, <<p11>>
| L4 — no rewrite: reuse `check`, or map at read time | the check shape (fix = remediation) / the query layer (virtual) | <<p7>>, <<p12>>
|===

*Argument for L2–L4 over L1*: the seven use cases in TODO-rules.adoc are all
instances of ~5 named refactorings (rename relation, move namespace, promote
attribute to type, deprecate, merge). IDEs won by shipping a *menu* of named,
well-tested refactorings — not a rewrite language. +
*Argument for L1*: only a general language covers the long tail *and* the
query verb; a catalog needs engine code per new shape and cannot express
"show me all tools that read gml". Counter: the general engine
(`RewriteRule` API) already exists and can stay — as the *implementation*
layer under a friendlier surface. +
*Argument for L1½*: most real queries and rewrites use exactly one variable
(the focus subject); ddot already has a way to refer to it — by omission.

*Resolution*: OPEN. Leaning: <<p13>> (focus queries) as the shared
query/check/rewrite surface for the common case, <<p6>>/<<p8>> catalog for
bulk migrations, L1 demoted to API + escape hatch. See coverage matrix in
<<r-surface>>.

[[i-surface]]
== ISSUE 1 — What surface syntax should rewrite rules have?

[[p1]]
=== Position 1 — Standalone DSL, ddot-shaped patterns (status quo, TODO-rules.adoc)

Keyword blocks `rewrite` / `when` / `remove` / `add` / `filter`; only the
patterns inside are `S ..P.. O`.

[source]
----
rewrite PromoteOnline
when   tool:$foo ..online.. yes
remove
add    tool:$foo ..has type.. online tool
----

*Pro*

* [+] Easiest to parse — a conventional line-oriented grammar, EBNF already drafted.
* [+] Familiar to anyone who knows SPARQL/SHACL; block roles are explicit words.
* [+] Already aligned with the `ddot check` Level 1 design (shared `when` grammar).
* [+] Maps 1:1 onto the `refactor` API (`RewriteRule`, `RemovalMode`, `Placement`).

*Con*

* [-] Not ddot.it. Violates the manifesto: keywords, block structure, a second
  grammar to learn ("there are deliberately no other features").
* [-] A `.ddotrules` file is *not* a ddot document — standard readers can't
  crawl it, `!!off` fencing / `,,` provenance / host embedding don't apply.
* [-] Two parsers to maintain forever (ddot reader + rule DSL).
* [-] Rules can't be annotated with ddot's own metadata mechanism.

[[p2]]
=== Position 2 — `!!` command regions ("ddot triples extended with !!commands")

Commands carry the structure; pattern/template lines are *plain ddot triple
lines* (standard triple regex, plus `$capture`/`?var` terms).

[source]
----
!!rewrite?name=PromoteOnline
!!when
tool:$foo ..online.. yes
!!remove
!!add
tool:$foo ..has type.. online tool
!!end
----

*Pro*

* [+] Consistent with existing precedent: `!!on`/`!!off` prove commands scope
  regions; `!!block?end=X` proves commands take `?key=value` params — so
  `!!rewrite?placement=end-of-file&mode=deprecate` needs no new directive syntax.
* [+] Pattern lines are genuine ddot lines → one triple-line parser for data,
  `check`, and `rewrite`.
* [+] Rules embeddable in any host document, like all ddot content.
* [+] `!!check` and `!!rewrite` become sibling verbs over the same inner grammar.

*Con*

* [-] Verbose: five command lines to say "replace one triple with another".
* [-] Section-role commands (`!!when`, `!!add`) are keyword blocks wearing a
  `!!` costume — structurally still Position 1.
* [-] `!!end` is a new closing-delimiter concept (only `!!block` has one today,
  and there it's implicit via blank line).
* [-] Ordering/nesting rules of the sub-commands must be specified (what if
  `!!add` precedes `!!when`?).

[[p3]]
=== Position 3 — The graph patch: `-` / `+` / bare / `~` prefixed lines

A rewrite rule *is* a diff over the graph, so write it as one. A `!!rewrite`
region contains ddot pattern lines with diff markers:

[source]
----
!!rewrite
- tool:$foo ..online.. yes
+ tool:$foo ..has type.. online tool
----

* `-` line — match *and remove* (the primary pattern)
* bare line — match only (join guard, never removed)
* `+` line — template to add
* `~` line — match and *deprecate* instead of delete

UC-4 (scoped rename with guard):

[source]
----
!!rewrite
?s ..has type.. Person
- ?s ..name.. ?o
+ ?s ..full name.. ?o
----

Add-only (UC-2) is a bare guard plus `+` lines; pure deletion is `-` lines
only. Filters as `? len(?o) >= 5` lines (or `!!filter …`). Params via
`!!rewrite?name=…&placement=end-of-file`.

*Pro*

* [+] Maximally compact: the entire `when`/`remove`/`deprecate`/`add`
  structure collapses into 1-character prefixes every developer already reads
  fluently (a generalized git patch).
* [+] Kills the "arrow spelling" open question of TODO-rules.adoc — there is
  no arrow; the `+`/`-` sugar of the draft becomes the *canonical* form.
* [+] Unifies with `check`: a `!!check` region with the *same* line grammar —
  bare = `when`, `+` = `must` exist, `-` = must `not` exist. One grammar, two
  verbs — the draft's stated goal, achieved at the syntax level.
* [+] Direct API mapping: `-`→`RemovalMode.DELETE`, `~`→`DEPRECATE`,
  bare→guard `TriplePattern`, `+`→add template.
* [+] Order-independent within a block (marker carries the role), except the
  first `-`/`~` line = primary — a single, simple rule.

*Con*

* [-] `-`/`+`/`~` prefixes are new syntax ddot.it never had; single-character
  markers are less self-documenting than words (though `!!rewrite` heads the
  block and the docs URL is one `ddot.it/rewrite` away).
* [-] A leading `-` could collide with hosts where lines start with `-`
  (Markdown lists, YAML sequences) — needs a "only inside `!!rewrite` regions"
  scoping rule (which is required anyway, see <<i-vars>>).
* [-] Diff intuition is imperfect: in a patch `-`/`+` are literal lines; here
  they are *patterns* with captures — the generalization must be taught.
* [-] Deprecate marker `~` has no diff precedent; pure invention.

[[p4]]
=== Position 4 — Rules as pure ddot triples (reification, zero new syntax)

Exploit "object MAY contain `..`" (syntax-summary pitfall 2): the whole
pattern lives in an object slot; a rule is an ordinary ddot block using
continuation lines.

[source]
----
rule:PromoteOnline ..has type.. rewrite rule
..when.. tool:$foo ..online.. yes
..remove.. primary
..add.. tool:$foo ..has type.. online tool ,, ..placement.. next-to-primary
----

*Pro*

* [+] Zero new syntax — the standard reader parses this *unchanged*; the rule
  engine merely interprets subjects typed `rewrite rule`.
* [+] Rules become first-class graph citizens: queryable (`ddot check` can
  lint your rewrite rules!), annotatable (`,, ..author.. mv ..since.. 2026-07`),
  linkable (`rule:X ..replaces.. rule:Y`), versionable like any other data.
* [+] Guest-language philosophy applied to rules themselves — a rule can live
  in a README next to the data it governs.
* [+] Natural interchange/storage format; other frontends can *generate* it.

*Con*

* [-] Patterns are strings-inside-objects → a second-level parse anyway; the
  "zero new syntax" is partly an illusion (the inner pattern grammar still
  exists, just hidden in object values).
* [-] Multiple `..when..` lines: graph edges are unordered; identifying the
  *primary* pattern must lean on line provenance — fragile after graph
  round-trips.
* [-] Reads indirect/meta; the one-triple-per-line elegance turns into
  triples-about-triples.
* [-] *Security*: rules-as-data means any crawled document can inject a graph
  rewrite — a code-injection channel. Must be mitigated by only honoring rules
  from explicitly passed `--rules` sources (see <<i-safety>>).

[[p5]]
=== Position 5 — One-liner sugar via `,,` metadata

For the 80 % case, a rule is a *single ordinary ddot line*; the metadata part
(which is allowed to contain `..`) carries the action:

[source]
----
tool:$foo ..online.. yes ,, ..rewrite to.. tool:$foo ..has type.. online tool
?s ..deprecated.. yes    ,, ..rewrite to.. nothing
tool:$foo ..?p.. ?o      ,, ..also assert.. tool:$foo ..has type.. tool
----

*Pro*

* [+] Already-valid ddot syntax; `,,` semantics ("annotates the whole triple")
  is exactly right — the annotation says what to *do* with the matched triple.
* [+] Replaces the draft's arrow sugar (`=>`, `+`, `-` one-liners) with a
  native mechanism; resolves that open question too.
* [+] Metadata is permissive (pitfall 4), so a full triple template fits with
  no escaping.
* [+] Perfect for rule *libraries* sprinkled inline next to the data they fix.

*Con*

* [-] Single-pattern rules only — no joins/guards, no filters; a block form is
  still needed (this is sugar, not a full position).
* [-] Overloads `,,`: a reader must distinguish rule-metadata from ordinary
  metadata (needs the `!!rewrite` region scope, or reserved relations
  `rewrite to` / `also assert`).
* [-] The pattern side *looks like* a data triple; outside a fenced region a
  normal collector would assert `tool:$foo ..online.. yes` as fact
  (see <<i-vars>>).
* [-] `nothing` as a magic object value is a special case to document.

== ISSUE 1, Round 2 — positions without (visible) variables

[[p6]]
=== Position 6 — Rewrite vocabulary: rules as schema-mapping triples

A fixed catalog of *standard rewrite relations*; a rule is an ordinary ddot
triple whose subject/object are relation names or namespaces. No variables —
the quantification lives in the relation's semantics.

[source]
----
name    ..renamed to..            full name ,, ..where type.. Person
tool:   ..namespace renamed to..  app:
online  ..promoted to type..      online tool ,, ..when value.. yes
old:x   ..merged into..           tool:x
online  ..relation deprecated..   use has type
----

*Pro*

* [+] No variables at all — the root cause of the Round-1 dislike is gone.
* [+] 100 % valid ddot today; the standard reader parses it; rules are
  queryable, `,,`-annotatable graph citizens (like <<p4>>, without the
  patterns-in-objects awkwardness).
* [+] Mirrors IDE refactoring menus and RDF precedent
  (`owl:equivalentProperty`, `dcterms:isReplacedBy`, ddot's own `same as`).
* [+] Each verb gets one precise, well-tested implementation — safer than
  arbitrary rule combinations.
* [+] Doubles as documentation: `name ..renamed to.. full name` stays true
  and useful *after* the migration (evolution history in the graph).

*Con*

* [-] Closed catalog: anything outside it needs engine code, not a rule.
* [-] Covers only the *rewrite* verb — no ad-hoc query, no general check.
* [-] Guards squeeze through `,,` metadata (`..where type.. Person`) — a
  mini-language regrows inside metadata.
* [-] Use/mention ambiguity: is `name` the relation or an entity called
  "name"? Needs a convention (`relation:name`?).
* [-] Same rules-as-data injection surface as <<p4>> (mitigated per <<i-safety>>).

[[p7]]
=== Position 7 — No rewrite language: `check` + `fix` (ESLint model)

Every rewrite is a *remediation of a check violation*. Extend the ddot-check
Level 1 shape with a `fix` block; `ddot check --fix` applies it.

[source]
----
shape PromoteOnline
when  ?t ..online.. yes            # the old form IS the violation
fix   remove
fix   add ?t ..has type.. online tool
----

*Pro*

* [+] One language, one tool, one rules file: lint gates CI, `--fix`
  remediates — the ESLint/clang-tidy model, strongly proven.
* [+] Every rewrite is automatically *justified* by a named violation →
  free dry-run report, free messages.
* [+] "Auto-fix" is already on ddot-check's COULD list; this just promotes it.

*Con*

* [-] Inherits check's Level-1 syntax — variables and keyword blocks, i.e.
  exactly the Round-1 style already disliked. Solves tool economy, not syntax.
* [-] Pure transformations (namespace migration) must be contorted into
  "violations" of a norm nobody stated.
* [-] No ad-hoc query verb either.

[[p8]]
=== Position 8 — CLI refactoring verbs; scripts as rule files

No file syntax at all: a fixed set of `ddot refactor` subcommands, one per
catalog shape (imperative twin of <<p6>>).

[source,sh]
----
ddot refactor rename-relation "name" "full name" --where "has type = Person"
ddot refactor move-namespace  "tool:" "app:"
ddot refactor promote         "online = yes" --to-type "online tool"
----

*Pro*

* [+] Zero new syntax; discoverable via `--help`; each verb maps 1:1 to a
  tested `RewriteRule` builder.
* [+] A shell script of these *is* a versionable, reviewable migration file.
* [+] Matches real usage: migrations are one-shot events, not long-lived
  rule bases.

*Con*

* [-] Not a language: no composition, no joins; `--where` reintroduces a
  mini-syntax through the back door.
* [-] Migration scripts live *outside* the corpus — not crawled, not
  queryable, not ddot.
* [-] Shell quoting of terms with spaces (`"pill label"`) is a constant papercut.
* [-] Rewrite only; query at best trivial lookups, check not at all.

[[p9]]
=== Position 9 — Refactoring by demonstration

No rule authoring: edit *one* instance by hand, then `ddot generalize <diff>`
lifts the concrete edit into a rule (interactively confirming what
generalizes), previews, and replays corpus-wide.

*Pro*

* [+] Zero syntax to learn — the "language" is editing ddot, which the user
  already knows. Example-first matches how people think ("like this one,
  everywhere").
* [+] Generalizing a one-line triple diff is tractable: align S/P/O, propose
  which differing slots become wildcards, confirm.

*Con*

* [-] Generalization is ambiguous (does `tool:figma` mean `tool:*` or *any*
  subject?) → needs interaction; not CI-able as the authoring path.
* [-] The derived rule still needs a stored representation (some other
  position) for audit and replay — this is a *frontend*, not a format.
* [-] Joins/guards are hard to demonstrate with a single example.
* [-] Rewrite only.

[[p10]]
=== Position 10 — Before/after snippet pair (diff by example)

Two plain ddot snippets; the engine computes the rule by *set-difference*:
line in both = guard, only-before = remove, only-after = add. (<<p3>>'s
semantics without markers.)

[source]
----
!!rewrite?example
X ..has type.. Person
X ..name.. N

X ..has type.. Person
X ..full name.. N
!!end
----

*Pro*

* [+] Both halves are plain ddot lines; reads naturally as "before → after".
* [+] No marker characters; roles are *derived*, not written.

*Con*

* [-] Placeholder names (`X`, `N`) are variables by *convention* — invisible
  syntax, the worst kind.
* [-] Fragile: a typo silently turns a guard into a remove+add pair; the
  duplication of unchanged lines invites drift.
* [-] Rewrite only.

[[p11]]
=== Position 11 — Host tables for bulk mappings

The bulk case (rename 30 relations in one vocabulary cleanup) as a host-format
table, ingested via host-specific extraction (precedent: Markdown `{#a .b}`):

[source,asciidoc]
----
.Relation renames
|===
| renamed from | renamed to
| name         | full name
| e-mail       | email
|===
----

*Pro*

* [+] For the most common real migration (bulk rename), a two-column table
  beats 30 rule blocks; readable and editable by non-programmers.
* [+] Host-specific extraction is an established ddot mechanism.

*Con*

* [-] Binary mappings only; guards/filters mean extra columns → a creeping
  spreadsheet language.
* [-] Per-host table parsing effort; rewrite only. A *frontend* for <<p6>>,
  not a standalone position.

[[p12]]
=== Position 12 — Virtual rewrite: map at read time, materialize on demand

Mapping triples (<<p6>> vocabulary) are applied by the *query layer*; files
stay untouched. `ddot materialize` optionally writes a file back when touched
(lazy migration).

*Pro*

* [+] Non-destructive; instant corpus-wide effect; write-back becomes
  incremental and reviewable per file.
* [+] Old files remain valid — the mapping *documents* their vintage.

*Con*

* [-] Two truths: the file says `name`, the graph says `full name` —
  provenance and grep get confusing.
* [-] Every consumer must apply mappings; materialization is eventually
  needed anyway → the complexity of both worlds.
* [-] An execution mode for <<p6>>, not a syntax; decides *when*, not *how*.

[[p13]]
=== Position 13 — Focus queries: the hole is the question, omission is the variable

Use two mechanisms ddot *already has*: an incomplete triple (today "silently
ignored") and the omitted-subject continuation line. Inside a `!!query` /
`!!check` / `!!rewrite` region, the missing slot *is* the question, and every
omitted subject refers to the same implicit *focus*:

[source]
----
!!query
..has type.. tool          # focus = every subject typed tool …
..reads.. gml              # … that also reads gml  (join via omission!)
----
[source]
----
!!check
..has type.. format        # focus selection
!!must
..has type.. gio:Format
..pill label..             # empty object slot = "some value must exist"
----
[source]
----
!!rewrite
- ..online.. yes           # focus + remove (markers from <<p3>>)
+ ..has type.. online tool # add; omitted subject = the focus, standard ddot sugar
----

*Pro*

* [+] Zero new term syntax: hole = question, omission = the only variable —
  both are existing ddot semantics, re-read in rule context.
* [+] *One surface for all three verbs* — query, check, rewrite differ only
  in the region command and the <<p3>> markers.
* [+] Matches the focus-node model (SHACL, ddot-check's `when`); most real
  queries and rewrites have exactly one variable.
* [+] Outside a fenced region these lines stay inert (incomplete → ignored),
  so <<i-vars>> largely dissolves.

*Con*

* [-] Exactly one variable: no multi-var joins (`?t reads ?fmt` ∧
  `?t writes ?fmt`) and no captures (`tool:$rest` → `app:$rest`) — needs an
  escape hatch (<<p14>>) for the long tail.
* [-] Empty-slot syntax is subtle: `..pill label..` (existence) vs
  `..pill label.. x` (value) differ by trailing content only; a *relation*
  hole collides with the untyped-link `.. ..` form.
* [-] Overloads continuation semantics: the same line means "fact about the
  previous subject" in data and "condition on the focus" in a rule region —
  context-dependent reading.

[[p14]]
=== Position 14 — ddot-ified SPARQL: full algebra, ddot surface

Take SPARQL 1.1 + Update *semantics* wholesale; spell them in ddot: patterns
are `S ..P.. O` lines, clause keywords are `!!` commands, no `{}`, no
`PREFIX` headers (ddot's `prefix` relation exists already).

[source]
----
!!select ?t ?fmt
?t ..has type.. tool
?t ..reads.. ?fmt
!!filter ?fmt =~ /^g/
----
[source]
----
!!delete
?t ..online.. yes
!!insert
?t ..has type.. online tool
!!where
?t ..online.. yes
----

*Pro*

* [+] Proven, complete semantics for *all three verbs* — SELECT/ASK = query,
  ASK-per-focus = check, DELETE/INSERT/WHERE = rewrite. Twenty years of spec
  work inherited; zero semantic design risk (joins, negation, OPTIONAL,
  paths, aggregates all have defined answers).
* [+] Compilable to real SPARQL → interop: run ddot queries against any RDF
  store, or SPARQL tools against a ddot corpus.
* [+] Consistent with ddot precedent: patterns are triple lines, structure is
  `!!` commands (like <<p2>>, but the keyword set is *standard*, not invented).
* [+] <<p13>> desugars into it cleanly — a progressive ladder like
  ddot-check's Level 0 → Level 1: +
  *L0* focus queries (no visible variables) → *L1* named `?vars`, flat
  conjunctive patterns (≈ the TODO-rules draft) → *L2* full ddot-SPARQL.
* [+] Nothing to document that SPARQL books don't already explain.

*Con*

* [-] Full SPARQL is *big*: OPTIONAL, UNION, subqueries, property paths,
  aggregates. Exposing it all buries "less is more"; curating a subset means
  the hard design work returns through the back door.
* [-] Variables everywhere — the original un-ddot feeling, now standardized
  rather than removed (mitigated only if <<p13>> is the default entry level).
* [-] SPARQL's algebra is a *tree* (nested groups); ddot lines are flat.
  OPTIONAL/UNION need block nesting that ddot has never had (`!!optional` …
  `!!end`? indentation? both alien).
* [-] RDF impedance: SPARQL assumes IRIs/literals/datatypes; ddot terms are
  bare strings with spaces. The mapping (via `prefix`) works but leaks.

[[p15]]
=== Position 15 — `!!find`: minimal-diff SPARQL

Take SPARQL as-is and change *only* what ddot's term model forces. Where
<<p14>> re-clothes SPARQL's clause structure in `!!` commands, P15 keeps
SPARQL's own keywords and braces and adds just an entry command and ddot
term delimiting. Less invention, more standard.

.The transformation rules
. *Terms → `..`-delimited.* SPARQL terms are self-delimiting
  (`<iri>`, `"literal"`, `?var`), so whitespace can separate them. ddot terms
  are free strings that may contain spaces, so the *separators* must delimit:
  every triple pattern is written ddot-style `S ..P.. O` — one pattern per
  line, no trailing `.`. Variables keep SPARQL spelling (`?name`); constants
  are plain ddot names.
. *Region: `!!find` opens, blank line closes.* A query starts with `!!find`
  on its own line. It ends at the *first blank line* — or at a custom
  terminator declared as `!!find?end=DONE` … `DONE` (precedent:
  `!!block?end=THE-END`). Matches ddot's block feel: no blank lines inside a
  unit.
. *Verb: optional LAST line, default `SELECT *`.* After the patterns, the
  region ends with what to *DO* with the matches: `SELECT …`, `ASK`,
  `DESCRIBE …`, `CONSTRUCT { template }`, `REPLACE { template }`. Omitted →
  `SELECT *`. The verb set is *open* — new capabilities arrive as new
  DO-verbs (`REPLACE`, `WARN`, `LAYOUT`, …) with the find-part unchanged. The `WHERE { }` wrapper is *dropped* — everything before the
  verb IS the where-group. Note the order is deliberately *reversed* vs
  SPARQL: first what to find, then what to do with it — the logical
  evaluation order (precedent: SQL's actual execution order, LINQ's
  `from…where…select`, KQL, PRQL).
. *`REPLACE` — the invented rewrite verb.* Defined as: DELETE what `!!find`
  stated, then INSERT the template. Per solution, the instantiated find
  patterns are deleted and the instantiated template triples inserted —
  SPARQL's `DELETE {P} INSERT {T} WHERE {P}` with the pattern stated *once*
  (SPARQL Update forces you to repeat it). An empty template (bare `REPLACE`
  or `REPLACE {}`) = pure deletion.
  Guards — patterns that must match but survive — go in
  `FILTER EXISTS { … }`, which by standard semantics matches without being
  part of the deleted patterns. Caveat: `FILTER EXISTS` cannot *bind*
  variables; a pattern whose value the template needs *and* that must
  survive is simply restated in the template (delete + re-insert = keep).
  Add-only is the natural sibling `INSERT { template }` (nothing deleted).
. *Functions — one syntax for extension AND data-typing.* `name(args)`.
  SPARQL's built-ins (`STRSTARTS`, `COUNT`, …) come along as-is; *extension
  functions* resolve to registered host-language implementations (Java in
  this lib) and are usable in `FILTER`, `BIND`, and in templates — computed
  values on the add side. The *same* syntax does typing, since ddot terms
  are untyped strings: `number(…)`, `date(…)`, `uri(…)` coerce/validate. In
  a `FILTER` that's a cast; in a *pattern term slot* it's a typed
  match-and-bind: `?f ..popularity.. number(?pop)` matches only objects that
  parse as numbers. No `"8"^^xsd:integer` literal syntax needed — functions
  replace datatype tags.
. *Braces are optional for the verb's template.* `CONSTRUCT` / `REPLACE` /
  `INSERT` may be followed by inline braces `{ … }` — or by plain
  triple-pattern lines, one per line, *until the blank line* (which
  terminates the region anyway). Not indentation-based: the blank line is
  the only delimiter. Match-side subtrees mid-query (`OPTIONAL { }`,
  `FILTER (NOT) EXISTS { }`, `UNION`) keep their braces — a braceless block
  there would have no end marker. The top-level conjunction never needs
  braces (one pattern per line replaces `.`-separation).
. *All other clauses keep SPARQL spelling*, one per line. Match-side clauses
  (`FILTER`, `BIND`, `VALUES`) stand among the patterns; solution modifiers
  (`GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`, `OFFSET`) follow the verb.
. *Convention: triple patterns are indented two spaces — keywords are not.*
  The indentation's job is to visually distinguish *query patterns* (and
  template lines) from the *fact-triples* that fill the rest of a ddot
  document: an indented triple-shaped line is a pattern, not a fact. Keyword
  lines are self-distinguishing and stay flush left — `!!find`, `FILTER`,
  `BIND`, `OPTIONAL`, `UNION`, the DO-verb and its solution modifiers.
  Purely a convention — ddot's whitespace freedom strips leading space,
  indentation never carries meaning.
. *No `PREFIX` header.* Names are ddot names; RDF expansion, when wanted,
  uses ddot's existing `prefix` relation.
. *`,,` on a pattern matches the triple's metadata.* More than sugar: ddot
  triples carry native metadata, so
  `?who ..leads.. Project Eagle ,, ..since.. ?y` is what SPARQL needs
  RDF-star (`<< ?who :leads :Eagle >> :since ?y`) for — ddot gets quoted-triple
  patterns for free.

[source,sparql]

!!find
  ?f ..seo id.. ?old

  ?f ..seo id.. slugify(?f)
----

==== Layout and warnings: the verb set is open

The DO-verb-last design extends without touching the find-part grammar: a
new capability is a new verb. Two more, motivated by the use case "per-type
property order in the source files, and warn on type conflicts":

*`LAYOUT`* — a write-back directive, not a graph operation. For each match,
the entity's property lines in its source file are stably reordered to
follow the *template line order* — the order of the lines IS the ordering;
no list syntax needed. A line with a relation variable (`..?other..`) marks
where all *unlisted* properties go (keeping their original relative order).
`LAYOUT` never adds or removes triples; it is an idempotent formatter
(`ddot fmt`).

*`WARN`* (and `ERROR`) — emit one message per match; the rest of the line is
the message, `?vars` interpolated (precedent: ddot-check's
`severity`/`message` directives). `ERROR` additionally fails CI.

.Q16 — type A: properties in order a, b, c, then everything else
[source]
----
!!find
  ?x ..has type.. A
LAYOUT
  ?x ..a.. ?_
  ?x ..b.. ?_
  ?x ..c.. ?_
  ?x ..?other.. ?_
----

.Q17 — type B: different order, different properties, "others" in the middle
[source]
----
!!find
  ?x ..has type.. B
LAYOUT
  ?x ..c.. ?_
  ?x ..name.. ?_
  ?x ..?other.. ?_
  ?x ..b.. ?_
----

.Q18 — warn when an entity is both A and B (layout would be ambiguous)
[source]
----
!!find
  ?x ..has type.. A
  ?x ..has type.. B
WARN ?x is typed both A and B — property layout is ambiguous
----

A type C with no `LAYOUT` rule is simply left untouched. When two `LAYOUT`
rules match the same entity, the engine does not reorder and reports the
conflict — which is exactly what Q18 makes visible up front.

Semantics notes: `LAYOUT` templates use `?_` in the object slot (the values
are irrelevant, only the relations order); a listed relation the entity
lacks is skipped, never created (`LAYOUT` is not `INSERT`). Like all
write-back, this composes with provenance: only lines in files the collector
may write are touched.

==== Arguments

*Pro*

* [+] Minimal diff from a proven standard: one entry command + one delimiting
  change. Anyone who knows SPARQL reads it instantly; every SPARQL tutorial,
  book, and LLM applies. Nothing to design semantically.
* [+] The default `SELECT *` with omitted verb makes the simplest query two
  lines (Q1) — nearly Level-0 ergonomics while full power stays reachable in
  the same syntax.
* [+] Patterns-then-verb reads as a pipeline — "find this, then DO that with
  it" — and matches the logical evaluation order (SQL's real execution
  order, LINQ, KQL, PRQL all made the same fix to SELECT-first). Variables
  are defined before they are used, which SPARQL gets backwards.
* [+] Blank-line termination is ddot's own block behavior; `!!find?end=`
  mirrors `!!block?end=` exactly.
* [+] `,,` patterns give RDF-star / reification *for free* (Q11) — a feature
  ddot has that SPARQL 1.1 lacks; zero syntax added.
* [+] Braces appear only at the complex end (Q8 is the first to need one
  inline); Q1–Q7 stay flat, one line per fact — visually ddot. With braceless
  blocks, a complete rewrite rule (Q12) contains *no* SPARQL punctuation at
  all — just `!!find`, indented triples, `REPLACE`, indented triples.
* [+] Compilable to standard SPARQL (interop with RDF stores), and the check
  use case is just Q7.
* [+] `REPLACE` improves on SPARQL Update: the pattern is stated once, not
  repeated in `DELETE` and `WHERE` (Q12); guards fall out of standard
  `FILTER EXISTS` semantics (Q13) — all three verbs now covered with one
  invented keyword.
* [+] One function syntax `name(args)` serves three needs at once: SPARQL
  built-ins, the host-language escape hatch every rule language eventually
  grows (registered Java functions in `FILTER`/`BIND`/templates, Q15b), and
  *data-typing* of ddot's untyped strings (`number(?pop)` as typed
  match-and-bind, Q15a) — no `^^xsd:` literal syntax needed. Also absorbs
  TODO-rules.adoc's implemented `len`/`count` filters and answers its open
  question about value functions on the add side.

*Con*

* [-] `REPLACE` maps only to `RemovalMode.DELETE`; *deprecate* mode and
  *placement* directives (TODO-rules.adoc) still need a home — plausibly
  `!!find?mode=deprecate&placement=end-of-file` params, but that's unspecified.
* [-] Namespace migration (UC-7, `tool:$rest` → `app:$rest`) is clumsy in
  pure SPARQL terms (`BIND`/`STRAFTER` string surgery); ddot's `prefix:$name`
  captures would have to be imported from Level 1.
* [-] UPPERCASE keywords, `FILTER(…)` expressions, and braces are un-ddot;
  the complex end (Q8–Q10) reads as "SPARQL with funny triples", and the
  manifesto's "no nesting" is given up beyond Q7.
* [-] A braceless template means a blank line inside a rule is fatal in a
  new way: it doesn't just end the region, it silently truncates the
  template. `!!find?end=` is the escape for long rules.
* [-] Term typing is lost: SPARQL distinguishes IRIs from literals from
  numbers; ddot has only strings. Largely mitigated by typing functions
  (`number(…)`, Q15a), but bare comparisons like `FILTER (?pop >= 8)` still
  need a coercion convention.
* [-] Extension functions make a rules file non-self-contained: it silently
  depends on a *function registry* (which Java functions exist, what they
  do); interop with real SPARQL engines needs a mapping to custom-function
  IRIs, and typed *pattern terms* (`number(?pop)` in a slot) don't compile
  to standard SPARQL at all. Host functions callable from rule files also
  sharpen the <<i-safety>> question.
* [-] Property paths (`:reads/:writes`, `:subTypeOf+`) clash with free-string
  relations — is `..reads/writes..` a path or a relation named
  "reads/writes"? Needs a rule; unresolved.
* [-] The FILTER expression sub-language (operators, functions, regex) is
  imported wholesale — a large surface hiding behind one keyword.

=== Resolution (Rounds 1+2, proposed)

Coverage of the three verbs (✓ full, ~ partial, – none):

[cols="3,1,1,1,3",options="header"]
|===
| Position | query | check | rewrite | role if adopted

| <<p1>> DSL (draft) | ~ | ✓ | ✓ | mental model + API only
| <<p3>> graph patch | – | ✓ | ✓ | marker syntax, reused by P13
| <<p6>> rewrite vocabulary | – | ~ | ✓ | catalog for bulk migrations
| <<p7>> check + fix | – | ✓ | ~ | `--fix` feature, not the language
| <<p8>> CLI verbs | ~ | – | ✓ | imperative twin of P6
| <<p9>> demonstration | – | – | ✓ | authoring frontend
| <<p10>> example pair | – | – | ✓ | rejected (invisible syntax)
| <<p11>> host tables | – | – | ✓ | bulk-rename frontend for P6
| <<p12>> virtual rewrite | – | – | ~ | execution mode, orthogonal
| <<p13>> focus queries | ✓* | ✓ | ✓* | *Level 0 surface* (*single focus var)
| <<p14>> ddot-SPARQL | ✓ | ✓ | ✓ | Level 2 semantics; clause structure ddot-ified
| <<p15>> `!!find` minimal-diff SPARQL | ✓ | ✓ | ✓ | *Level 2 surface* (`REPLACE` = Update half)
|===

Proposed synthesis — a progressive ladder, one algebra underneath:

. *Level 0 = <<p13>>*: focus queries/checks/rewrites with no visible
  variables — holes and omission. Covers the everyday 80 %.
. *Level 1*: add named `?vars` and `prefix:$captures` to the same flat line
  grammar (≈ TODO-rules draft, <<p3>> markers for rewrite). Multi-var joins,
  namespace migration.
. *Level 2 = <<p15>> surface over <<p14>> semantics*: define L0/L1 as sugar
  over a curated ddot-SPARQL subset; full power (OPTIONAL, UNION, aggregates)
  only here. P15's `!!find` (keep SPARQL keywords; ddot-delimit terms;
  DO-verb *last* with default `SELECT *`; verb templates braceless — pattern
  lines until the terminating blank line) is the concrete surface; `REPLACE { template }` — delete what `!!find` matched,
  insert the template — is the rewrite verb; `name(args)` functions bridge to
  host-language code and double as datatypes.
. *Catalog on top = <<p6>> (+ <<p8>>, <<p11>> frontends)*: standard rewrite
  relations for the named, bulk refactorings — each defined as a macro
  expanding to a Level-1/2 rule.
. <<p7>>'s economy is kept: `check` and `rewrite` (and `query`) are three
  verbs over the *same* pattern grammar; <<p12>> stays an execution-mode
  decision, taken separately.

*Status: OPEN* — Round 1's resolution is superseded; the ladder above is the
current leaning, not a decision.

[[i-vars]]
== ISSUE 2 — Variables: ddot.it has none. How do rule files avoid becoming data?

A line like `?s ..name.. ?o` is, to a normal reader, a *perfectly valid
triple* about an entity named `?s`. Pitfall 6 ("prose accidentally becomes
triples") cuts the other way here: rules would accidentally become data.

=== Position 2a — `!!rewrite` regions act like `!!off` for plain readers

*Pro*: one rule, works in any host document; readers already implement
region skipping. +
*Con*: readers must know the `!!rewrite` command even if they don't implement
rewriting (acceptable: skipping is trivial).

=== Position 2b — Dedicated file extension (`.ddotrules`)

*Pro*: crawlers exclude by extension, zero reader changes. +
*Con*: kills in-document rules, contradicting the guest-language philosophy;
doesn't help when someone pastes a rule into a README.

=== Position 2c — Do nothing; `?s`-triples are harmless noise

*Pro*: zero work; "more is better" manifesto tolerates noise. +
*Con*: `tool:$foo ..online.. yes` in a Position-5 one-liner is NOT harmless —
it asserts a plausible-looking fact. Rejected.

*Resolution*: 2a (regions are opaque to non-rewrite readers), with 2b as a
convention on top for pure rule files.

[[i-safety]]
== ISSUE 3 — Safety: may crawled documents contribute rules?

Rules-as-data (P4, and in-document P3/P5 regions) = any document in the
corpus can inject a graph rewrite.

* *Position 3a — honor rules only from explicit `--rules` files/args.* +
  Pro: no injection channel; mirrors `ddot check --rules`. Con: in-document
  rules become dead weight unless explicitly listed.
* *Position 3b — honor in-document rules from allow-listed paths/regions.* +
  Pro: keeps the guest-language story. Con: allow-list config is a new
  concept; easy to misconfigure.
* *Position 3c — honor everything, rely on `--dry-run` preview.* +
  Pro: simplest. Con: preview fatigue → rubber-stamping; rejected.

*Resolution*: 3a now; 3b later if in-document rules prove useful.

[[i-primary]]
== ISSUE 4 — Which pattern is the primary (removal target)?

* *P4a — first `-`/`~` line in the block* (Position 3). Pro: explicit marker,
  order rule trivial. Con: none significant.
* *P4b — first `when` line* (TODO-rules.adoc). Pro: matches draft. Con: role
  depends on position, not marker; breaks under reordering.
* *P4c — line provenance in reified form* (Position 4). Pro: works without
  markers. Con: fragile after graph round-trips.

*Resolution*: P4a. In the reified form (P4), the removal target is the
`..remove.. primary` / `..deprecate.. primary` object referencing an explicit
`..when..` — no reliance on ordering.

== Consequences for TODO-rules.adoc (if the ladder is adopted)

* The draft's grammar survives as *Level 1* — but re-clothed: `!!` region
  commands instead of keyword blocks, <<p3>> markers instead of
  `remove`/`add` sections, and defined as sugar over ddot-SPARQL (Level 2)
  rather than as a standalone language.
* Scope widens from `rewrite` to three verbs — `query`, `check`, `rewrite` —
  over one pattern grammar; ddot-check Level 1 merges into the same ladder.
* Open question "arrow spelling" — dissolved (markers / Level-0 omission).
* Open question "one parser with check" — strengthened to "one parser and one
  algebra for query/check/rewrite".
* The API mapping table stays valid unchanged; `RewriteRule` becomes the
  compile target of Levels 0–2 and of the <<p6>> catalog macros.
* Term grammar (`?var`, `?_`, `prefix:$name`, `~`/`=~` constraints) and
  `filter` semantics carry over verbatim — from Level 1 upward; Level 0 has
  no visible terms beyond constants and holes.
