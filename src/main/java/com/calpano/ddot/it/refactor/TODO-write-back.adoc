= Layered write-back architecture (draft)
:icons: font
:toc:
:toclevels: 3

DRAFT. How to make write-back respect the same *layering* the readers already use:
an outer host-language reader (Markdown, AsciiDoc, HTML) handles coarse block
structure and delegates the *inner* content to the ddot.it parser. Write-back must
run the same layering in reverse: the inner ddot replacer edits a *snippet*, and the
outer reader maps that snippet edit back onto the real source.

This supersedes the "line-based readers only" first cut (see `use-cases.adoc`),
which works only when a triple's source line is verbatim in the file.

== The layering, as it already exists (reading)

The read pipeline is already two-layer (grounded in `basereader.markdown`):

[source]
----
file bytes
  → OUTER host reader        (MarkdownParser: blocks, headings, lists, code fences)
      emits block callbacks   onPlainLine / onCodeBlock / onSectionAttributes
      with ABSOLUTE line nums
  → bridge                    (StructureHandler + StructuredSource2TripleEvents)
      blockStart()/blockEnd() demarcate a snippet; forwards each inner line
  → INNER ddot parser         (Source2TripleEvents.onLine(text, lineNumber))
      emits ITripleEvent with provenance (resourceUri, lineNumber)
----

Two things the outer layer already does that break a naive line writer:

* *Stripping* — the host syntax is removed before the inner parser sees the text (a
  list item `* a .. p .. b` is handed down without the `* `; a fenced block without
  the fences).
* *Synthesizing* — `onSectionAttributes` builds a triple line
  (`sectionTitle .. type .. value`) that **does not exist verbatim** on any source
  line. Its provenance line points at the heading, not at a writable triple line.

So a triple's `(resourceUri, lineNumber)` is a coordinate in the *inner, stripped*
view — not always a byte range you can overwrite in the file.

== The principle: write-back is the read pipeline reversed

[source]
----
inner triple edit  (rename / add / delete / deprecate, in ddot terms)
  → INNER ddot serializer     produces the new inner line(s) for a snippet
  → SNIPPET edit              "in snippet S, replace inner line k with «text»"
  → OUTER host reader         maps snippet coords → file coords, re-applies host
      syntax (list bullet, heading attr, fence) and returns a real source edit
  → SOURCE edit               byte-level change to the file (atomic, previewable)
----

The inner layer never touches the file. It speaks *snippet coordinates*; the outer
layer owns the snippet↔source mapping and is the only thing that writes bytes.

== The snippet model

A *snippet* is one block-level unit the outer reader extracted and stripped: a
paragraph, a list item, a fenced code block, a section heading's attribute list.
It is the granularity at which host syntax can be cleanly added/removed. (Inline
formatting inside a snippet — bold, links — is *not* unified; see caveats.)

A snippet needs a *bidirectional* mapping:

[cols="1,1,3",options="header"]
|===
| Direction | Used for | What it maps

| forward  | reading    | source line/col → snippet inner line/col
| inverse  | write-back | snippet inner edit → source line/col range (+ host re-wrap)
|===

For the *line-based* readers (`.ddot`, and Markdown plain-line triples) the mapping
is the identity: snippet == file, inner line == source line. That is precisely the
case the current `LineBasedSourceWriter` already handles — it becomes the leaf
implementation, not a separate mechanism.

== Proposed interfaces (Java sketch)

[source,java]
----
/** A stripped block the inner parser consumed, with a mapping back to the source. */
interface ISnippet {
    String resourceUri();
    List<String> innerLines();               // host-stripped text handed to the inner parser
    int sourceLineOf(int innerLine);         // inverse map for existing inner lines
    SnippetKind kind();                       // PLAIN | LIST_ITEM | CODE_BLOCK | HEADING_ATTR | ...
}

/** The inner layer emits edits in snippet coordinates; it never writes files. */
sealed interface SnippetEdit {
    record ReplaceInner(ISnippet s, int innerLine, String newText) ...
    record DeleteInner (ISnippet s, int innerLine) ...
    record InsertInner (ISnippet s, int afterInnerLine, String newText) ...
}

/** The outer host reader realises snippet edits as byte-level source edits,
 *  re-applying its own syntax (bullet, heading, fence) and handling inserts. */
interface IHostWriter {
    List<SourceEdit> toSourceEdits(List<SnippetEdit> edits);   // returns the existing SourceEdit list
}
----

`GraphRewriter.plan` already yields the inner intent (rename/add/delete/deprecate).
The step to add is: emit `SnippetEdit`s (via each triple's snippet handle) instead
of `SourceEdit`s directly, then let the matching `IHostWriter` lower them to
`SourceEdit`s that `LineBasedSourceWriter` writes.

== Responsibilities

[cols="1,3",options="header"]
|===
| Layer | Owns

| OUTER host reader (md/adoc/html)
| block extraction + stripping; the snippet↔source mapping; realising a
  `SnippetEdit` as a `SourceEdit` (re-wrapping host syntax, choosing where/how an
  inserted inner line becomes a real list item / paragraph / fenced line); which
  snippets are *writable* at all.
| INNER ddot layer
| parse/serialize triples; compute rename/add/delete/deprecate as edits in snippet
  coordinates; dedup, placement, provenance — everything already in `refactor`.
| leaf (`.ddot`, plain-line)
| identity mapping: snippet == file, `LineBasedSourceWriter` writes directly.
|===

== Inserts across the boundary

Adding a triple is the hard direction: the new inner line must be *wrapped* in host
syntax by the outer reader — a new `* s .. p .. o` bullet in a list, a new line in a
code fence, a new paragraph. Placement (`NEXT_TO_PRIMARY` / `END_OF_FILE`, already
in `RewriteRule`) chooses the anchor; the host writer chooses the *decoration*. Some
snippet kinds may be *append-only* or *read-only* for write-back (e.g. a synthesized
heading-attribute triple → refuse to rewrite, report as skipped).

== Caveat: inline formatting is not unified

Only *block-level* host syntax is stripped and re-applied. Inline formatting (bold,
italics, links, inline code) inside an object value is left byte-for-byte as-is:
unifying it across md/adoc/html is not worth it. Consequences:

* a rewrite may only touch the *ddot structural* tokens (subject / `..` / relation /
  object boundary), never reflow inline markup;
* if an object value contains inline markup, prefer *in-place token edits* over
  re-serialising the whole value (the `use-cases.adoc` fidelity question resurfaces
  per-snippet); or mark such triples read-only for write-back.

== Provenance enrichment required

`ISourceLocation` (today: `resourceUri` + one `lineNumber`) must grow a *snippet
handle* (or snippet id + inner-line offset), so a triple can be traced to
`(snippet, innerLine)` and the outer reader can invert it. Readers already know the
block boundaries (`blockStart`/`blockEnd`); they need to *retain* the snippet and its
mapping rather than only forwarding absolute line numbers. Backwards-compatible:
line-based readers set snippet = whole file, innerLine = sourceLine.

== Migration path

. Keep `LineBasedSourceWriter` as the leaf writer (identity snippet).
. Introduce `ISnippet` + `SnippetEdit` + `IHostWriter`; have `GraphRewriter` emit
  `SnippetEdit`s, and a trivial identity `IHostWriter` reproduce today's behaviour
  for `.ddot`.
. Enrich provenance with the snippet handle; make Markdown retain snippets.
. Implement `IHostWriter` for Markdown (list items, plain lines), then AsciiDoc.
. Mark non-invertible snippets (synthesized headings) read-only → `skipped`.

=== Implemented (first increment, 2026-07-04)

A lighter realization of the above — a per-line *mapping* instead of a full snippet
object — is in, and makes write-back *safe* on host files:

* `LineMapping` (`source` package): `Verbatim` (identity) / `Wrapped(prefix,suffix)`
  (re-wrap, e.g. `<!-- … -->`) / `Synthesized` (no writable line → skip).
* `ISourceLocation.mapping()` carries it (defaults to `Verbatim`, so `.ddot` and
  plain-line host triples are unaffected). The outer reader sets it per block via
  `Source2TripleEvents.currentLineMapping(...)`; it resets on block/subject/resource
  boundaries.
* `GraphRewriter.plan` honours the mapping: non-writable → `skipped` (never
  corrupts); writable → the edit text is run through `mapping.toSourceLine(...)`.

Per-reader mapping (both readers now pass the exact wrapper for single-line comments):

[cols="1,2,2",options="header"]
|===
| Reader construct | Mapping | Write-back

| plain line (`.ddot`, `.md`, `.adoc`)      | `Verbatim`            | rewritten in place
| fenced code (```` ``` ````), `----` source, `////` comment blocks | `Verbatim` | rewritten in place
| list item (`- `, `* `, `+ `, `1. `; adoc `* `, `- `, `. `) | `Wrapped(marker,"")` | bullet stripped on read, re-applied on write
| single-line comment (`<!-- … -->`, `// …`)| `Wrapped(prefix,suffix)` | rewritten, re-wrapped
| clean multi-line `<!-- … -->` (delimiters alone) | `Verbatim`     | rewritten in place
| messy multi-line `<!-- … -->` (delimiter shares a content line) | `Synthesized` | skipped
| `!!block` multi-line object (spans lines) | `ISnippet.block` (span) | rewritten/deleted as a whole-span `ReplaceSpan`
| heading attrs / resolved `link:` macro    | `Synthesized`         | skipped (no writable line)
| HTML / XML / YAML triples                 | `Synthesized` (reader default) | skipped (bullet still stripped on read)
|===

List items are handled by a shared `basereader.ListMarker` (Markdown/HTML and
AsciiDoc bullet grammars). The bullet is stripped before the triple parser (else it
leaked into the subject) and recorded as a `Wrapped(marker, "")` mapping so write-back
re-applies it. `resetLineMapping()` restores the default *without* resetting the
active subject, so continuation across list items (`* ..likes.. Carol`) still works.
Single-char AsciiDoc markers can never match a ddot `..` continuation, so those stay
intact.

Bug fixes in this pass:

* *Block off-by-one* — the Markdown fenced-code and AsciiDoc `----`/`////` block
  parsers reported content starting at the *delimiter* line, so a block triple's
  provenance was one line too high. For Markdown code blocks (already `Verbatim`)
  this was a latent *corruption* bug — write-back would have overwritten the fence.
  Fixed: block content now starts at the first content line; those blocks are
  writable in place.
* *Structured readers defaulted to `Verbatim`* — HTML/XML/YAML triples are parsed
  from structure, not verbatim lines, so write-back would have corrupted those
  files. Added `Source2TripleEvents.defaultLineMapping(...)`; these readers now
  default to `Synthesized` (skip).

Also in:

* *Robust writer* — `LineBasedSourceWriter` resolves all edits against original line
  indices and rebuilds the file once, so any same-line combination (replace+insert,
  delete+insert, multiple inserts) applies unambiguously; still atomic (temp+rename).
* *Rule sets* — `GraphRewriter.plan(graph, List<RewriteRule>)` merges a whole rule
  set against one snapshot: identical edits de-duplicate, and two structural edits on
  the same `file:line` conflict (first wins, rest reported in `skipped`).

=== ISnippet graduation (implemented)

The per-line `LineMapping` has graduated to a span-capable *snippet* — the object
model from "The snippet model" above, realized for our data:

* `ISnippet` (`source` package): `startLine()`/`endLine()` span, `writable()`, and
  `decorate(ddotLines) → sourceLines` (the host-writing step). Two impls:
  `LineSnippet` (a single line, decorated by a `LineMapping` — the degenerate,
  common case) and `BlockSnippet` (a multi-line `!!block` object, command line
  through terminator; ddot serialization is already multi-line so it passes
  through). `ISourceLocation.snippet()` carries it (defaults to a verbatim line).
* `DdotLineSerializer.serializeLines(...)` is block-aware: a newline-bearing object
  is re-emitted as `S ..P.. !!block?end=MARKER` + content + a generated marker
  guaranteed not to collide with the content.
* `SourceEdit.ReplaceSpan(uri, start, end, newLines)` replaces a whole line range
  (empty `newLines` deletes the span); the writer applies it in the same
  index-stable rebuild. `GraphRewriter.plan` emits `ReplaceLine`/`DeleteLine` for
  single-line snippets and `ReplaceSpan` for multi-line ones, transparently.

So `!!block` triples — previously read-only for write-back — now rewrite, deprecate
and delete correctly (`WriteBackTest.blockObjectTriple_*`), and the model is ready
for any future multi-line snippet (the `IHostWriter` role lives in the readers,
which build the snippets). What is *not* yet built is cross-kind *insertion*
decoration (below).

Tested across formats: plain-line, fenced/`----`/`////` block, single-line comment,
and clean multi-line comment rewrites with prose preserved and re-index fixed point;
messy multi-line comment, `link:` macro, and HTML triples skipped-not-corrupted;
rule-set merge + conflict; same-line delete+insert (`MarkdownWriteBackTest`,
`AsciiDocWriteBackTest`, `StructuredReaderWriteBackTest`, `WriteBackTest`,
`GraphRewriterTest`).

== What remains (not blocking; needs new demand)

Write-back is complete for the formats and cases above. The open items all require a
capability that does not yet exist upstream:

* *Cross-kind insertion decoration* — a rewrite that *adds* a triple next to an
  anchor reuses the anchor's mapping (a new bullet next to a list item, a plain line
  next to a plain line). That is right for same-kind inserts, but decorating an added
  triple with a *different* host construct (e.g. inserting a new list item where the
  anchor was a heading) needs the full `ISnippet`/`IHostWriter`. Rewriting and
  deleting existing list items, comments and blocks is done.
* *Dependent, ordered rule application* — `plan(graph, rules)` evaluates every rule
  against the same snapshot. Rules that must see each other's changes need
  materialize-between-rules (apply to the graph, re-plan), plus a fixed-point loop.
* *Accepted re-serialize limitations* (from the "re-serialize the line" decision):
  `ddot.it/this` expands to its URI, only the first `,,` meta pair survives, and
  touched lines are normalized to canonical spacing — the `..` hugs the relation
  (`S ..P.. O`, matching the ddot syntax summary), not the loose `S .. P .. O`.
  Switching a rule to a minimal-token patch would preserve these but was
  deliberately out of scope.

== Open questions

. *Snippet identity across re-index* — a snippet handle must survive re-parsing (or
  be recomputed) so a plan made against one index applies to the file on disk.
. *Where do `ISnippet`/`IHostWriter` live* — in each `basereader.*` (outer), with the
  inner `refactor` layer depending only on the interfaces.
. *Multi-triple snippets* — a code block with many triples: edits are batched per
  snippet, then per file (still bottom-up).
. *Round-trip fidelity* per host — the fixed-point test (re-index reproduces the
  rewrite) must hold per reader, not just for `.ddot`.
