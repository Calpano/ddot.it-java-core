= Knowledge-graph refactoring — requirements & use cases
:icons: font
:toc:
:toclevels: 3

Requirements for a *refactoring* layer over a ddot.it knowledge graph: rename ids
and relations, add and remove triples, all conditioned on a triple pattern with
bound variables. This document defines the *semantics* (the API-level model). The
concrete surface *syntax* for expressing rules is deliberately **not** fixed yet —
we build the API and the requirements first, then design the syntax.

Status: DRAFT. The Java API sketched here lives in
`com.calpano.ddot.it.refactor` (see `GraphRewriter`, `RewriteRule`,
`TriplePattern`, `MatchTerm`, `TripleTemplate`).

== Purpose

Knowledge graphs built by indexing a folder of files drift: relations get
renamed, id conventions change, boolean attributes should become types, sources
use synonyms. We want *safe, repeatable, pattern-driven* transformations —
"refactorings" — that operate on the whole graph (or a scoped subset) rather than
by hand-editing source files.

== Prerequisites (already present)

These exist and are assumed by everything below:

* *Folder indexing* — per-extension readers (`basereader.*`: ddot, Markdown,
  AsciiDoc, HTML, XML, YAML) turn files into triples. The folder-walk/watch driver
  is *reused from the app* (`../ddot.it-java`: `LocalIndexer`, `FileSystemSource`,
  `IndexCommand`) — this library does not duplicate it. Refactoring operates on the
  `Kgraph` the indexer produces.
* *Provenance* — every node and edge records `sourceLocations()`
  (`resourceUri` + `lineNumber`); ingestion attaches the location to the edge and
  both endpoint nodes (`TripleEvent2Kgraph`). So every triple remembers *where it
  came from*.
* *Per-source update* — `IKgraph.removeBySource(resourceUri)` removes what a file
  contributed (keeping entities with other provenance). Re-index = remove + re-read.

Refactoring is the next layer: transform the *indexed* graph.

== Core model

A *rewrite rule* has two parts:

. a *condition* — a triple pattern `(?s, ?p, ?o)` that selects matching triples and
  binds variables, and
. *effects* — remove the matched triple and/or add new triples built from the
  bound variables and literals.

[source]
----
RewriteRule
  condition : TriplePattern (s-term, p-term, o-term)
  removeMatched : boolean
  add : List<TripleTemplate>   // each = (s-out, p-out, o-out)
----

=== Match terms (condition)

Each of the three positions in the condition is a *match term*:

[cols="1,3",options="header"]
|===
| Term | Meaning

| *literal* `"online"`         | matches that exact id
| *variable* `?s`              | matches anything, binds the value to `s`
| *wildcard* `_`               | matches anything, binds nothing
| *constrained variable*       | matches + binds only when the value satisfies a
                                 string constraint (see below)
|===

=== String-match on a variable

The tricky requirement from use case 2: a variable that only matches values
passing a *string test*, e.g. "subject starts with `tool:`". Supported string
constraints (a `StringMatcher`):

* `equals(x)` — exact
* `prefix(x)` — starts-with (case-sensitive)
* `suffix(x)`
* `regex(re)` — Java regex; enables future *capture groups* (e.g. bind the part
  after `tool:`)

`tool:$foo` in the informal syntax means "bind the subject, require prefix
`tool:`". Because the current use cases reuse the *whole* subject in their output,
whole-value binding is enough; named capture of the *suffix* (`$foo` = the part
after `tool:`) is a documented future extension (regex capture groups).

=== Output terms (added triples)

Each position of an added `TripleTemplate` is an *output term*:

* *constant* `"has type"` — a literal id
* *variable reference* `?s` — the value bound by the condition

Resolution substitutes bindings into the template to produce a concrete triple
`(from, predicate, to)`, which is added as an edge.

=== Effects & semantics

* *Remove* — when `removeMatched` is set, the matched edge(s) are removed
  (index-maintained). Provenance rules of `removeEdge` apply.
* *Add* — added edges are created via the normal node/edge machinery.
* *Dedup* — adds are structurally de-duplicated by default (same label + same
  endpoints), so a rule that fires for many matches does not create N copies of the
  same asserted triple (essential for use case 2). Uses the existing
  `IKgraph.addEdge(edge, forceCreate=false)`.
* *Provenance carry-over* — an added triple inherits the `sourceLocations()` of the
  matched triple that produced it, so `removeBySource` and re-indexing stay
  consistent, and the new triple is attributable to the same origin.
* *Snapshot-then-apply* — matches are collected first, then effects applied, so a
  rule never sees its own additions (no infinite cascades within one `apply`).
* *Idempotency* — running an add-only, deduped rule twice yields the same graph.

== Write-back to source [CHOSEN — design open]

A rewrite changes the *materialized* graph, but the *source files* still say the
old thing. **Decision: rewrites must be written back to the source files** — that is
the point of refactoring (a materialized-only view would be re-clobbered on the next
index). The engine currently mutates the graph; write-back is the next layer, and
its design has several open issues.

.Decisions (2026-07-04)
[cols="1,3",options="header"]
|===
| Issue | Decision

| A. Provenance/scope | *Line-based readers first* — `.ddot` + line-oriented
  Markdown/AsciiDoc triples (one triple = one source line). Defer HTML/XML/YAML.
  The writer re-reads the source line at the recorded `lineNumber` to get raw text.
| B. Added-triple placement | *Next to the primary match* by default (insert after
  its source line); a rule may override to end-of-file or a sink.
| C. Rename | *In-place token edit* — patch just the changed token on the original
  line (minimal diff, preserves formatting + `,,` meta).
| D. Staleness | Batch edits *per file*, apply *bottom-up* (descending line number).
| G. Safety | *Dry-run preview* (produce a diff), apply only on explicit confirm;
  atomic temp+rename writes.
|===

=== Implemented (first cut, 2026-07-04)

* `GraphRewriter.plan(graph, rule)` computes a `SourceEditPlan` (`ReplaceLine` /
  `DeleteLine` / `InsertAfter` / `AppendToFile`) from primary-edge provenance,
  without mutating the graph or any file. In-place rename detection, add dedup, and
  non-`file:` provenance reporting (`skipped`) are in.
* `LineBasedSourceWriter.preview(plan)` renders a diff; `.apply(plan)` writes files
  surgically — per file, edits bottom-up, atomic temp+rename.
* `DdotLineSerializer` re-emits a single triple as one ddot line (round-trip tested).
* End-to-end + *fixed-point* tested: index a `.ddot` file → plan → apply → re-index
  reproduces the rewritten graph (`WriteBackTest`).

Per-rule *placement* (`RewriteRule.Placement.NEXT_TO_PRIMARY` | `END_OF_FILE`, via
`withPlacement`) and *deprecate-instead-of-delete* (`RewriteRule.deprecating()`,
which keeps the old line annotated `,, ..status.. deprecated` and still adds) are
wired and tested.

Known limitations of the first cut (all tracked below): only one `,,` meta pair
survives per line (so deprecating a triple that already had meta keeps only the
`status` marker); `ddot.it/this` subjects are expanded to their URI on re-serialize;
a triple with multiple `file:` provenances is written to the *first* only. The
deeper limitation — that write-back only handles *line-based* readers — is what the
layered architecture in `TODO-write-back.adoc` addresses.

=== The core constraint: mixed-content files

Sources are rarely pure `.ddot`. Triples are *embedded* in Markdown, AsciiDoc, HTML
prose. So a whole-file re-serializer (like the ddot.it-js `serializeGraph`) is
**not** an option for the general case — it would delete the prose. Write-back must
be *surgical*: edit only the exact source spans that the changed triples came from,
leaving everything else byte-for-byte intact. Pure `.ddot` files are the easy
special case of the same mechanism.

=== Open issue A — provenance is currently too coarse

`ISourceLocation` records only `resourceUri` + a single `lineNumber`. Surgical edits
need more:

* the *span* (start+end line) — block literals span many lines; a triple is not
  always one line;
* the *original raw text* — the graph stores *normalized* ids (`ddot.it/this` →
  the resource URI; untyped → `links to`), so you cannot find the source token by
  searching for the stored id;
* whether the subject was *explicit* or a *continuation* (`.. p .. o` with the
  subject carried over) — deleting/moving such a line is not local.

Likely need: enrich provenance to a *source span* (start line, end line, and enough
raw text / token offsets to locate and replace the triple), emitted by the readers.

=== Open issue B — where do ADDED triples go?

An added triple has no source line yet. Options: (a) next to the primary matched
triple (its provenance file+line — natural for rename/promotion); (b) appended at
the end of the origin file; (c) a dedicated generated sink file/block. Rename-style
rewrites want (a) *in place*; brand-new asserts (UC-2) want (b) or (c).

=== Open issue C — rename = in-place token edit vs delete+insert

`(?s knows ?o)` → `(?s is friend of ?o)` is ideally a *one-token edit* on the
original line (minimal diff, preserves formatting/meta), not "delete line + append a
new line elsewhere". The engine models this as remove+add; the writer should
recognise the in-place case and patch the token.

=== Open issue D — line-number staleness & batching

Editing a line shifts the line numbers of everything below it, invalidating other
provenance in the same file. Writer must *batch per file* and apply edits
*bottom-up* (or recompute offsets).

=== Open issue E — formatting fidelity & fixed point

Minimal-diff: touch only changed triples; preserve surrounding whitespace and `,,`
meta. Correctness criterion: after write-back, *re-indexing the file reproduces the
rewritten graph* (a fixed point) — the round-trip test.

=== Open issue F — non-file & multi-provenance sources

Write-back is only possible for `file:` sources; remote/other schemes must be
skipped or reported. A triple with provenance from *several* files (same triple in
two places): does a removal edit all of them, or detach one?

=== Open issue G — safety

Editing user files is destructive and hard to reverse. Wants: a *dry-run* that
produces a diff/preview, explicit confirm-then-apply, and atomic writes (temp +
rename) with optional backup.

=== A note on "deprecate instead of delete"

The `REMOVED`/`ADDED` annotations in UC-1 suggest a softer model: keep the old
triple but mark it deprecated (`removeMatched=false` + add `..deprecated.. yes` or a
`,,` status) rather than deleting the source line. This side-steps much of issue C
and is worth offering as a per-rule option.

== Worked use cases

=== UC-1: promote a boolean attribute to a type

Every triple `tool:$foo ..online.. yes` should be **removed** and replaced by
`tool:$foo ..has type.. online tool`.

[cols="1,3"]
|===
| condition     | `(?s prefix "tool:")  ..  "online"  ..  "yes"`
| removeMatched | `true`
| add           | `(?s)  ..  "has type"  ..  "online tool"`
|===

Result: the `online/yes` fact is retracted; each matching tool gains
`has type = online tool`, attributed to the original triple's source.

=== UC-2: assert a type for a whole id-namespace (string-match on a var)

Every `tool:` subject, regardless of its predicate/object, should assert
`..has type.. tool`.

[cols="1,3"]
|===
| condition     | `(?s prefix "tool:")  ..  ?p  ..  ?o`
| removeMatched | `false` (keep the original data)
| add           | `(?s)  ..  "has type"  ..  "tool"`
|===

The key is the *string-match on `?s`* (prefix `tool:`) and *dedup*: a tool with 10
properties still gets exactly one `has type tool`.

== Brainstormed refactoring use cases

Grouped by kind. All are expressible as one or more `RewriteRule`s (some need
future extensions, flagged).

=== Rename / canonicalize

* *UC-3 Rename a relation* everywhere: `..knows..` → `..is friend of..`.
  (`(?s knows ?o)` → remove + add `(?s "is friend of" ?o)`.)
* *UC-4 Scoped relation rename* [IMPLEMENTED]: rename only where a guard holds,
  e.g. `..name..` → `..full name..` only for `Person` subjects — a *multi-pattern
  join*: primary `(?s name ?o)` + guard `(?s has type Person)`.
* *UC-5 Collapse synonyms*: `..works for.. | ..employed by.. | ..works at..` → one
  canonical `..works at..` (condition predicate = *one-of* set; a small
  `StringMatcher.oneOf` extension).
* *UC-6 Rename a node id*: `alice` → `person:alice` in both subject and object
  positions (two rules, or the existing `IKgraph.mergeNodes`). Label carry-over is
  a refinement.
* *UC-7 Namespace / prefix migration* [IMPLEMENTED]: rewrite every id matching
  `tool:(?<rest>.*)` to `app:${rest}` — regex *named capture* on the condition
  plus an output *template* (`OutTerm.template`).
* *UC-8 Normalize ids/relations*: lowercase, trim, de-space — id hygiene.

=== Add / assert

* *UC-9 Blanket type assertion by namespace* (= UC-2).
* *UC-10 Attribute → type promotion* (= UC-1).
* *UC-11 Default value if missing*: for every `?s has type tool` with no
  `?s online ?x`, add `?s online unknown` (needs *negation-as-failure*; future).
* *UC-12 Symmetry closure*: for `?a sibling of ?b` add `?b sibling of ?a`.
* *UC-13 Inverse relation*: for `?a parent of ?b` add `?b child of ?a`.

=== Remove / clean up

* *UC-14 Delete by pattern*: remove all `?s deprecated yes` (pure removal).
* *UC-15 Retract negatives*: remove `?s online no`.
* *UC-16 Deprecate instead of delete*: keep the triple but add
  `,, ..status.. deprecated` / a companion `..deprecated.. yes` (model-3 variant of
  UC-1).

=== Restructure

* *UC-17 Reify an attribute into a node*: `x ..address.. "..."` →
  `x ..has address.. addr1`, `addr1 ..value.. "..."` (introduce a central node —
  cf. `migrate.adoc` splitHyperedgeCentralNode).
* *UC-18 Literal → entity extraction*: `x ..author.. "Jane Doe"` →
  `x ..author.. person:jane-doe` + `person:jane-doe ..label.. "Jane Doe"`.
* *UC-19 Split a multi-valued object*: `x ..tags.. "a,b,c"` → three
  `x ..tag.. a|b|c` (object tokenization; needs a value-splitter function; future).
* *UC-20 Merge duplicate entities*: `alice`, `Alice`, `person:alice` → one node,
  remapping all edges (`mergeNodes`).

=== Normalize values

* *UC-21 Unit/format normalization*: `x ..price.. "10 EUR"` →
  `x ..price.. 10` + `x ..currency.. EUR` (value parsing; future).
* *UC-22 Bulk retype*: `?s has type OldType` → `?s has type NewType`.

=== Scope by provenance

* *UC-23 Source-scoped refactor*: apply a rewrite only to triples from a given
  source file (combine the rule with a `sourceLocations()` filter) — e.g.
  re-namespace everything imported from `legacy.md`.
* *UC-24 Project a subgraph*: copy triples matching a pattern into a new graph
  (extract/slice).

== Open questions

. *Surface syntax* — how does a user write a rule? Candidates: an extended ddot.it
  line with `?vars` and a `==>` arrow; a small JSON/YAML rule file; a fluent Java
  builder (already available via the API). To be designed after the API settles.
. *Multi-pattern conditions (joins)* [DONE] — the engine ANDs several patterns with
  shared variable bindings (nested-loop join); the first pattern is the primary/
  target, the rest are guards.
. *Regex capture groups* [DONE] — `StringMatcher.regex` binds named groups
  `(?<name>...)`, and `OutTerm.template("app:${name}")` recomposes them on output.
. *Negation-as-failure* — "add if missing" (UC-11) needs "no triple matches".
. *Value functions* — split/normalize (UC-19/21) need pluggable string functions on
  bound values.
. *Write-back to source* — persistence model (2) above; blocked on the ddot.it
  line-syntax serializer.
. *Rule sets & ordering* — running many rules: fixed-point iteration? one pass?
  conflict handling?
